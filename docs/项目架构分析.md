# 智能语音助手 - 项目架构分析

## 1. 项目概述

智能语音助手是一款基于大语言模型的桌面应用，通过语音/文字对话控制电脑操作。

**技术栈**：
- 前端：React + TypeScript + Vite + Tailwind CSS + Electron
- 后端：Node.js + Express + Socket.IO
- AI服务：阿里云千问（DashScope API）
- 通信：WebSocket（Socket.IO）

### 2.2 核心数据流

```
用户语音 → Web Speech API → 文本 → Socket.IO → 后端
    ↓
后端接收 text-command
    ↓
ConversationController.handleTextCommand()
    ↓
SessionStore 记录用户消息
    ↓
LLMService.invokeLLM() → 千问API
    ↓
解析响应 → 判断是否有 toolCalls
    ↓
├── 有工具调用 → SafetyService 校验 → ToolRouter 执行 → 返回结果
│                                                        ↓
│                                              需要确认？→ 发送确认请求
│                                                        ↓
│                                              直接执行 → 返回执行结果
│
└── 无工具调用 → 直接返回文本响应
    ↓
TTSService 语音合成（千问TTS WebSocket）
    ↓
Socket.IO 发送 audio-chunk / audio-response
    ↓
前端 AudioContext 播放音频
```

## 5. 技术栈评估

### 5.1 Node.js 保留价值分析

**优势**：
1. **实时通信**：Socket.IO 原生支持，WebSocket处理成熟
2. **前后端统一**：TypeScript/JavaScript全栈，开发效率高
3. **Electron集成**：与前端Electron无缝集成
4. **NPM生态**：丰富的包管理和工具链
5. **异步I/O**：非阻塞模型适合实时应用

**劣势**：
1. **系统控制**：需要调用shell命令，不如Python直接
2. **AI生态**：相比Python的AI/ML生态较弱
3. **本地模型**：运行本地大模型支持不如Python

### 5.2 Python 引入价值分析

**优势**：
1. **AI生态**：Hugging Face、LangChain、本地模型支持
2. **系统控制**：pyautogui、win32gui 等成熟库
3. **MCP协议**：Anthropic MCP SDK 主要是Python实现
4. **蓝牙支持**：ESP32通信、pyserial等
5. **数据处理**：NumPy、Pandas等科学计算库

**劣势**：
1. **实时通信**：需要额外框架（FastAPI + WebSocket）
2. **部署复杂**：需要Python环境
3. **性能**：GIL限制多线程性能

### 5.3 Node.js + Python 共存方案

**推荐架构**：

```
┌─────────────────────────────────────────────────────────────────┐
│                         前端 (Electron + React)                  │
└─────────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────────┐
│                    Node.js 网关层 (保留)                         │
│  - Socket.IO 实时通信                                            │
│  - 前端静态资源服务                                               │
│  - 请求路由和负载均衡                                             │
│  - 会话管理                                                      │
└─────────────────────────────────────────────────────────────────┘
                              │
              ┌───────────────┼───────────────┐
              ▼               ▼               ▼
┌─────────────────┐ ┌─────────────────┐ ┌─────────────────┐
│  Node.js 服务   │ │  Python 服务    │ │  Python 服务    │
│  (现有功能)     │ │  (MCP控制)      │ │  (本地模型)     │
│                 │ │                 │ │                 │
│ - 千问API调用   │ │ - 系统控制      │ │ - Llama/Qwen   │
│ - 基础TTS      │ │ - 应用适配插件  │ │ - 离线推理     │
│ - 文件操作     │ │ - 蓝牙通信      │ │ - 指令缓存     │
└─────────────────┘ └─────────────────┘ └─────────────────┘
```

**通信方式**：
- Node.js ↔ Python：HTTP REST API 或 gRPC
- 进程管理：Node.js 使用 child_process 启动 Python 进程

## 7. 已知问题

### 7.1 暂停播放Bug

**问题描述**：前端点击暂停播放按钮后，UI状态变化（"播放中"提示消失），但浏览器语音仍在播放。

**根本原因**：`useSocket.ts` 中的 `stopSpeaking` 函数虽然尝试停止音频，但存在以下问题：
1. 音频队列清空后，正在播放的音频源可能未被正确停止
2. `AudioContext.close()` 是异步操作，可能在关闭前新的音频已开始播放
3. 后端可能仍在发送音频块，前端需要通知后端停止

**修复方案**：见后续修复章节。
